# 10 · 迭代模板（修 bug / 评审 / 加需求）

**适用时机**：功能上线后的日常迭代。
**用法**：选一个模板，把 `<>` 里的内容替换掉，其余原样保留。**不要在原始提示词后面追加要求**——那会让上下文越滚越脏。

---

## 模板 A：修 bug（最小改动）

```text
【现象】<一句话描述你看到的错误现象>
【复现】<具体步骤：点哪里 → 输入什么 → 看到什么>
【期望】<应该是什么样>
【实际】<实际是什么样，贴报错原文/截图描述>
【范围】<哪个工具/哪个面板区域/哪条链路>

要求：
1. 先定位根因，用一句话说清"为什么会这样"，再动手。不要直接改代码。
2. 只改和这个 bug 直接相关的代码。不许顺手重构、不许调整无关的样式、不许升级依赖。
3. 改完给出：改动行数、改了什么、为什么这样改能修好。
4. 回归验证：这个 bug 的复现步骤现在是什么结果 + 相邻的 2 个功能没被影响。
5. 如果你判断根因在 DSH 宿主而不是插件里，停下来告诉我，不要绕过它打补丁。
```

---

## 模板 B：代码评审（让它挑自己的刺）

```text
【任务】以严格评审者的视角，审查 data-analysis 插件的当前实现。不要改代码，只出问题清单。

按这五个维度逐条过：
1. 正确性：边界条件（空数据、单行、全 null、超大值、时区、夏令时）、并发（两个导入同时跑）、幂等（重复导入/重复点击）。
2. 安全：路径、SSRF、SQL、表达式、凭据、XSS、资源耗尽。每条都要指出具体代码位置。
3. DSH 契合度：有没有绕开 slot 直接操作 DOM、有没有硬编码颜色、有没有 import 宿主 client 包、cleanup 是否完整、locale 是否齐全。
4. 可维护性：重复逻辑、超长函数（> 80 行）、隐式耦合、魔法数字。
5. 性能：N+1 查询、全量读盘、无上限的数组增长、每次渲染重算。

输出格式：表格（严重度 P0/P1/P2 | 位置 文件:行 | 问题 | 建议改法）。P0 不超过 3 条，多了说明你在凑数。
最后回答一个问题：如果只修 3 处，你修哪 3 处，为什么。
```

## 模板 C：加一个小需求

```text
【需求】<一句话>
【为什么要】<用户场景，一句话>
【约束】不新增依赖；不改 Dataset / ChartSpec 的既有字段（只能加可选字段）；不影响已保存的数据集和图表。

要求：
1. 先说这个需求会影响哪些文件、哪些已有行为，等我确认再改。
2. 改动保持向后兼容：旧 meta.json / 旧 chart spec 仍能打开。
3. 加一个能验证这个需求的验收步骤（具体到点什么）。
```

---

## 模板 D：性能优化

```text
【现象】<哪个操作慢，多慢，数据量多大>
【目标】<期望降到多少>

要求：
1. 先测量再优化：给出优化前的基线数字（用真实数据量，不要用 100 行测）。
2. 定位瓶颈在哪一层（解析 / 聚合 / 渲染 / 序列化），用数据说话，不要猜。
3. 一次只改一个点，改完重新测，贴前后对比。
4. 不许用"减少功能"换性能（比如偷偷把 limit 从 10000 降到 1000）。
5. 如果瓶颈是架构性的（比如内存聚合撑不住），直接说"这需要换存储方案"，不要局部优化糊过去。
```

---

## 模板 E：把它拉回正轨（AI 开始跑偏时）

```text
停一下。你现在偏离了约束，回到 00 号宪法：
1. 你刚才写的 <具体行为：比如自己实现了一个 modal / 改了 packages 下的文件 / 引入了 echarts> 违反了第 <N> 条。
2. 撤销这部分改动，回到上一个可运行的状态。
3. 重新说明你打算怎么做，先不要写代码。
另外：如果你不确定某个 DSH API，先跑 cordis_inspect_query，不要再凭记忆写。
```

---

## 使用建议

- **一次只用一个模板**。混着用（"顺便修个 bug 再加个功能"）是返工的起点。
- 修 bug 时把**报错原文**贴全，不要转述。转述会丢掉最关键的那一行。
- 评审模板每月跑一次，比出事之后再查便宜得多。
- 模板 E 很有效：大多数跑偏不是能力问题，是它在长上下文里忘了约束。明确点名"第 N 条"比笼统说"你不对"有效十倍。
```
